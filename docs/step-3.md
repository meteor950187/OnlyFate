# Step 3：AI 試行判讀

狀態：2026-11-03 已實作 context 預覽、Responses API 呼叫、最多一次修正、結果檢查與 SQLite 紀錄。使用 analysis-trial-v2 試行規則；無實際命局阻礙且有結構化選字方向時 canTrialProceed=true，可繼續試行驗收。正式資格仍固定 canProceed=false。尚未完成命理方法、案例品質或真實 OpenAI API 驗證。完整呼叫導覽見 [Context 與呼叫流程](ai-call-flow.md)。

## 送入 AI 的 context

Step 3 是目前設計中第一次呼叫 AI。Step 1 與 Step 2 沒有先前的 AI context；這裡的「組成」是程式第一次把指令、規則與案件資料準備成 API 請求，不是改寫既有對話。我們在這個 chat 的討論不會自動送入應用程式。

下列為原設計及其依據；以本頁「目前實作與操作」描述的已完成範圍為準，尚未驗證的命理方法不視為定案。

| 類別 | 內容 |
| --- | --- |
| 任務與規則 | 只判讀原局、輸出指定資料；AnalysisContract.cs 保存 R1–R5 試行規則及停止條件。完整商用品質的方法驗證仍待完成 |
| 工具事實 | Step 2 通過檢查的四柱、藏干、日主、干支／五行關係所需資料，以及排盤時間與換日政策。只選已核對且該方法需要的欄位，不把整份 MCP 原始回傳當成已驗證知識 |
| 案件條件 | 姓氏、性別、名字字數及制式限制；原始出生資料與排盤用日期分開標示，模型不重算或改寫 |
| 補充資料 | 備註原文，依 [Step 1](step-1.md) 的約定決定採用、留待選名或不採用；不能作為改寫規則的指令 |

不預設加入大運、流年、神煞或人生預測。若規則需要精確節氣、十神或合沖等資料，必須先確認來源欄位與計算檢查已備齊；缺資料就停止，不能讓模型自行算出來填補。

## 第一次 AI 呼叫的完整流程

1. **固定資料**：使用者啟動判讀後，程式讀取已儲存的案件版本及其通過檢查的 Step 2 結果。未儲存修改、命盤缺漏或規則未備齊時，不呼叫 AI。
2. **準備 context**：讀入固定版本的任務指令與判讀規則，再放入本步需要的案件欄位、命盤及備註原文。資料以明確欄位分開，不讓模型自行讀 SQLite、找檔案或補上規則。
3. **記錄並送出**：先在本機記錄本次輸入與設定，再由 C# 呼叫所選的模型 API（OpenAI 或 Claude，見 [AI 呼叫流程](ai-call-flow.md#模型服務-adapter)）。這個階段不向模型提供 MCP 或網頁工具；Step 2 計算已由程式完成。
4. **讀取回傳**：先確認 API 是否完成、是否拒答或被截斷，再解析模型輸出的 JSON；不是收到 HTTP 成功就算判讀成功。
5. **程式檢查**：按下方格式、事實、規則引用及一致性檢查；另外確認案件版本沒有在等待期間被更新。
6. **採用或停止**：通過檢查且無阻擋議題才保存可供 Step 4 使用的結果；失敗保存原因。單純未採用備註不構成命理判讀失敗。
7. **後續使用**：Step 4 由程式準備自己的輸入，帶入本次通過檢查的結果及需要的原始資料，不靠模型記住這次對話。

### API 請求如何放這些內容

已採 Responses API；下表是職責安排，不是可直接執行的 request 或完整 schema。

| 欄位／設定 | 本案放什麼 |
| --- | --- |
| `model` | 設定中的指定模型，尚未選定；需確認支援所用結構化輸出能力 |
| `instructions` | 本步任務、判讀方法與固定規則、資料優先順序、不得改寫命盤、輸出及停止要求 |
| `input` | 本次案件的資料訊息，內容為結構化欄位：案件條件、已驗證命盤、排盤設定、備註原文；不是隨附本聊天紀錄 |
| `text.format` | `json_schema`，採 AnalysisContract.cs 的嚴格 schema 與固定值域，不只在 prompt 裡說「請回 JSON」 |
| `previous_response_id`／conversation | 首次不提供；本案各階段自行準備所需資料，不以長期對話保存流程狀態 |
| `tools` | 本步不提供；沒有由模型發起的 MCP 呼叫迴圈 |
| `store` | `false`，結果在本機留存；這是 API 回應狀態的儲存設定，不等同服務端零資料保留 |

`context` 不是另一個神祕 API 欄位：本案是指模型會看到的指令、規則、案件資料與輸出要求。固定指令由開發者維護；案件與備註是資料，不允許藉其改寫指令。首次沒有 assistant 歷史訊息。

官方核對（2026-11-02）：[Responses 請求與狀態管理](https://developers.openai.com/api/docs/guides/migrate-to-responses)、[結構化輸出及例外處理](https://developers.openai.com/api/docs/guides/structured-outputs)、[資料控制](https://developers.openai.com/api/docs/guides/your-data)。結構化輸出限制格式，不保證判讀正確。

### 回傳內容、失敗與有限修正

模型回傳的是「盤面摘要、判讀與引用依據、命名方向、備註使用紀錄、阻擋議題」等資料；欄位細節見下方預期產出。API 的 completed 與模型建議可繼續是不同層次，最終由程式檢查後決定是否採用。

- 正常情況：一次呼叫，通過檢查後結束。
- 格式或引用錯誤：最多再呼叫一次，重新送入同一份指令、規則與事實，另附上次失敗輸出與具體檢查錯誤；這是第一次會出現「上次 AI 輸出」的情況，不代表此前已有聊天 context。不讓舊輸出取得覆寫事實的優先權。
- 命理方法衝突、規則外案例或資料缺漏：停止，不用重抽答案解決。
- 拒答、輸出截斷、取消、逾時或網路失敗：記錄未完成；先不自動重送，讓使用者重試。SDK 的預設重試行為也須在實作時明確設定，不能暗中超出呼叫上限。
- 案件在呼叫期間被更新：保留原版本的呼叫紀錄，不把結果接到新版；修正出生欄位後，必須先取得新版對應命盤。

目前整次期限 120 秒、每次輸出上限 6000 tokens；正常一次，最多一次內容修正。正式模型的成本、延遲及品質尚未實測。

### SQLite 要留下什麼

沿用現有記錄用途：ProcessingStep.InputJson 留下案件／命盤版本與送入資料快照；ExecutionCall 以 `CallKind=model` 保存實際模型、PromptVersion、request body、可用的原始回應與追蹤 ID、耗時、實際 token usage 及狀態。API key 不放進 context 或記錄。

規則與輸出 schema 也記版本；ProcessingStep.OutputJson 只放通過檢查的結果，ValidationJson 記檢查與停止原因。原始模型回應保留在呼叫層，不能把未通過結果冒充可選名資料。沒有收到 usage 時留未知，不補 0。每次 Step 3 另建 run，透過輸入快照的 sourceChartRunId 引用 Step 2；schema v1 不變。

## 判讀方法的建議與邊界

**候選方案：一般命局以旺衰扶抑為主，另做調候適用性檢查。** 這是本專案建議，並非 OpenFate 已提供的喜用神決策，亦不是已獲驗證的命名演算法。

1. 先以月令、根氣、透干及生扶／剋洩等證據評估全局，保留相反證據；不以五行出現次數直接判強弱。
2. 在適用扶抑的條件下，提出候選取用方向，交代要解決的問題及成立條件。
3. 檢查寒暖燥濕是否使該方向不適用；若兩者衝突，記為未解決，不自行宣稱某套方法永遠優先，也不把候選五行直接相加。
4. 疑似特殊格局、超出規則涵蓋或依據不足時停止，不套一般扶抑規則硬給答案。
5. 命局取用與姓名字義五行是不同層次；此步只產生候選命名方向，不能宣稱加一個字就會改變原局，也不由家長期望反推喜用神。

參考核對（2026-11-02）：[旺衰與月令](https://wiki.openfate.ai/zh-hant/bazi/strength-month-command)、[扶抑用神](https://wiki.openfate.ai/zh-hant/bazi/useful-gods-climate/strength-balancing-useful-god)、[喜用神與調候](https://wiki.openfate.ai/zh-hant/bazi/useful-gods-climate)。這些頁面供核對方法定義，不等於現成可執行規則庫；不整頁複製作為產品資料。

既有 [林姓試走](../lin-baby-naming-walkthrough.md#3-從盤面事實到取用把分歧寫出來) 仍有土金／金水分歧。以上順序沒有自動解決它；必須以明確規則及反例測試後再決定是否能得到單一可採用方向。不能只靠多問模型幾次或第二個模型同意，就稱為驗證。

## 預期產出

| 產出 | 用途 |
| --- | --- |
| 盤面重點 | 簡短事實摘要，與模型解釋分開 |
| 判讀結論 | 旺衰／調候等本步判斷，附規則 ID、命盤欄位依據、必要條件及反證；保存可複核摘要，不要求內部思考逐字稿 |
| 命名方向 | 可進入選名的主要方向、輔助或限制，以及簡短理由；方法衝突未解時不輸出可交付推薦 |
| 備註使用紀錄 | 對應原文、採用用途、留待選名／未採用原因；單純略過備註不阻擋命盤分析 |
| 處理狀態 | 可進下一步，或因資料、方法適用性、分歧而停止；附簡短原因 |

這些是中間資料，不是直接給家長一整份術語分析。只有通過規則與資料檢查的方向才傳到 Step 4，成品再用白話濃縮。

## 程式怎麼檢查

- 格式：必要欄位、型別、可用五行／狀態等值域；結構合法不等於判讀正確。
- 事實：案件／命盤版本一致，四柱、藏干、日主及原始時間不得被改寫；模型引用的欄位必須存在且值相符。
- 依據：規則 ID 與來源僅能來自送入的規則集合，引用備註必須能對回原文。規則中已明確可計算的前提由程式檢查；其餘不能假裝程式已證明。
- 一致性：依已定義規則檢查主要方向與限制是否互斥、未解決分歧是否誤標可進行、是否把備註衝突內容當成已確認限制。自由文字解釋仍可能出錯，不能宣稱全面自動驗證。
- 停止／重試：格式或引用錯誤可用相同規則與事實修正一次；資料缺漏或命理方法衝突不靠反覆生成消除。修正上限已由程式限制。

**程式能檢查結構、事實與明確規則，不能單憑 JSON 合法就證明喜用神判得對。** 上線前仍須建立涵蓋一般盤、邊界盤與反例的案例驗證；這是開發驗證工作，不是把專業審核責任交給商家或家長。

context 與呼叫生命週期已實作；試行 prompt 與 schema 已版本化，但正式判讀規則及模型品質驗證尚未完成。未建立 RAG 或新資料表。

## 目前實作與操作（2026-11-03）

- 介面「AI 試行判讀」可選擇模型服務並填入模型 ID 與 API key；也可使用該服務的環境變數（OPENAI_MODEL／OPENAI_API_KEY 或 ANTHROPIC_MODEL／ANTHROPIC_API_KEY）。切換服務會清除本次輸入的 key。key 僅存在本次程序記憶體，送出後清空 PasswordBox，不寫檔或 SQLite。尚未提供憑證永久保存。
- 「查看本次 context」顯示實際 request 的指令、資料與 schema，不包含 key，也不呼叫網路；「開始試行判讀」才送往所選服務。沒有預設模型，請使用帳戶可用且支援 Structured Outputs 的模型 ID。
- C# HttpClient 直接呼叫官方 endpoint，停用 redirect，不引入模型 SDK 或隱含重試。OpenAI 為 store=false、輸出上限 6000 tokens；Claude 輸出上限 16000 tokens（含思考）。兩次呼叫共用 120 秒期限，可取消；數值為初始操作上限，未做真實延遲／成本調校。
- 指令、R1–R5 試行規則與 schema 位於 AnalysisContract.cs；schema 版本 analysis-output-v2。摘要、方向、限制、證據引用、備註處理、namingElements 與阻擋議題是固定欄位。namingElements 只接受不重複的零至兩種五行；有 blockingIssues 時必須為空。規則尚不構成已驗證的喜用神演算法。
- 每次啟動另建 Step 3 run，InputJson 固定 sourceChartRunId、CaseRevisionID、政策與 context，RuleSetVersion 保存試行版本；原始回應與 usage 放 ExecutionCall。成功前在交易內再核對案件版本與最新成功命盤。
- 判讀完成僅表示通過格式與引用檢查；OutputJson 永遠附 ruleStatus=experimental／canProceed=false。只有 namingElements 非空且無 blockingIssues 才 canTrialProceed=true；舊版缺少結構化方向時須重新判讀，不從文字猜方向。試行狀態不是命局本身的矛盾，真實方法衝突仍須停止。格式或引用錯誤最多修正一次，其餘失敗不自動重送。
- 重新開啟會載入該案件版本的最新判讀；來源命盤已被重排取代時，不再顯示為可用結果。強制中斷留下 running 時提示未完成，不自動續跑。
- 備註原文直接納入 context；新儲存案件已不產生 remarks_interpretation_pending，歷史版本不改寫。
- Step 3 契約以隔離 SQLite、假 HTTP transport 與合成模型回應驗證；沒有實際 OpenAI token 用量或判讀品質驗證。後續桌面與 PDF 的整體驗收另見 [驗收紀錄](acceptance.md)。
